# jst-ai-agent 能力沉淀设计

本版为架构和建设规范。2026-10-07 已落地商品/主仓库存、有效销售明细/日序列及库存错配核对入口，详见 sales-stock.md；第二批采购加工未结、收货及原料单号关联见 supply-review.md，第三批参数化补货/补产情景见 replenishment-plan.md，后续逐域验收。可执行能力以 SKILL.md 和代码为准；未创建数据库或后台任务。

## 目标与完成标准

让同一套可信业务事实支持不同经营问题；新增模块时复用接入与指标，避免每次临时抓取、重新解释状态或重写公式。保留已实现的默认口径；企业规则按公司隔离，行业流程按需加载。

设计完成标准：明确每层职责和调用关系、能力状态及数据契约、模块流程与示例、现有文件归属和分阶段验收。执行能力只有完成代码、数据核对及相应验证后才可标记已支持。

## 四层分工

| 层 | 负责什么 | 输出 | 放在哪里 |
| --- | --- | --- | --- |
| 数据读取 | 会话、身份、已核实只读接口、筛选、分页、白名单字段、源状态和来源 | 带范围及质量信息的业务记录 | 项目代码；接入契约放 company-metrics.md/data-blueprint.md |
| 指标与计算 | 规范化、去重、单位、状态口径、关联、汇总、需求情景和预测数值 | 指标值/结果表、口径版本、计算依据、缺项 | 项目中的可复用函数；指标定义先放 company-metrics.md |
| 模块分析 | 问题拆解、数据门槛、诊断顺序、原因核对、情景选择、行动优先级 | 有证据的解释、候选行动、待核对项 | analysis-workflow.md、replenishment.md、factory-analysis.md |
| 任务入口与交付 | 识别意图、选流程、调用能力、按需加载参考、中文回答及必要报告 | 用户可理解、可追溯的答案 | SKILL.md 路由；交付规则复用 analysis-workflow.md |

数据调用链：问题 → 选模块与口径 → 检查所需能力 → 读取 → 确定性计算 → 分析 → 交付。已有简单查询沿最短路径执行，不强制生成完整诊断报告。

skill 是任务指南和调用入口；实际读取、数值计算和后续必要存储留在项目。当前单文件代码及 query.sh 可以继续使用，仅在新增实际能力需要时拆分。暂不建立插件框架、独立微服务或为六个模块复制六套接入。

## 数据读取能力的粒度

按业务实体设计稳定入口，底层接口和表单细节由接入代码封装。用户和模块不直接传任意 URL、Cookie 或任意字段表达式。

| 业务实体 | 最小读取内容 | 当前边界 |
| --- | --- | --- |
| 商品 | 普通/组合装 SKU、名称、启用、款式、单位、业务分类/货权映射 | catalog可执行；分类/单位/货权需核对 |
| 销售订单明细 | 订单/明细标识、SKU、数量、状态、业务类型、赠品、业务时间、渠道 | 月排行、有效明细及日序列可执行；金额及全历史未验收 |
| 库存 | 仓库×SKU×读取时刻，各实际/虚拟/占用/冻结字段及其关系 | 主仓在售及实物扣占用核对可执行；多仓/锁定/完整履约待接入 |
| 采购及入库 | 单头与 SKU 明细、有效剩余、仓库、供应商、计划/实际到货、收货关联 | 当前非归档未结SKU、收货对账可执行；采购头量额外补充/归档/交期待验收 |
| 加工及收货 | 单头与明细、加工前后 SKU、投入/产出、已收/剩余、状态、业务关联 | 当前未结产出SKU、原料单号关联与收货核对可执行；逐行BOM/实耗/批次工序未接 |
| 库存流水、BOM、售后 | 唯一明细、业务关联、时间、数量、关系版本等 | 按各域实际契约核实，不能由上述记录推造 |
| 工序、质量、成本和财务 | 批次事件、报工/质检、成本凭据、账务及收付款关联 | 先确认其他已用模块/生产系统是否有记录，再决定接入或补采集 |

“商品数量”属于计算能力，不替代商品读取；“月销量前十”属于汇总能力，不替代全量订单明细。跨模块分析复用底层事实，Top N 只限制展示，不能截断参与计算的数据。

### 每个读取能力的契约

至少记录：业务 ID、来源页面/接口和方法、筛选是否生效、字段白名单与含义、唯一键、关联键、时间字段/时区、数量单位、状态语义、分页方式、权限/归档覆盖、核对方式、最后验证时间及入口。

请求范围由公司、期间、实体/仓库/店铺和必要字段确定；先按问题选范围，再分批读取。只读 POST 回调不能仅凭 HTTP 方法判断为写操作，必须验证业务方法；也不能把所有 POST 视为可读。

未来新增读取结果的共同元信息建议包含：

- `run_id`、公司、实体、源契约版本、请求筛选、读取开始/结束时间。
- 业务日期范围、仓库/渠道、归档覆盖；明确请求范围与可分析范围。
- 读取行数、唯一记录数、分页完整性、必需字段完整性、状态/单位异常及警告。
- 白名单投影后的记录，或分批记录位置；凭证、客户收货信息不进入结果。

沿用现有 `ok`/`complete`，保持向后兼容；新元信息逐项增加，不为设计先改旧输出。`complete` 只描述请求范围分页是否完整，不能代替字段质量、历史覆盖或跨域时点一致性。

全量结果过大时，确定性代码读入必要记录并输出聚合、异常和追溯 ID，不把所有订单塞进模型上下文。当前订单仍在内存处理；后续若业务需要本地历史底座，先明确范围、投影和保留方式，按项目约定建设，不默认保存原始订单。

### 能力状态

一个接口的状态不能直接决定整个模块已可用。分别记录数据、计算、分析三类能力的状态：

| 状态 | 含义 | 允许的表达 |
| --- | --- | --- |
| 规划 | 有目标但无已核实读取契约/实现 | 需要核实什么、预期支持什么 |
| 已探测 | 页面或小范围请求可读，字段初步可见 | 存在这些记录；尚不保证全量/明细/语义 |
| 已验证 | 契约、限定范围完整读取及对账通过 | 可以在明确覆盖范围内复用；未必有稳定任务入口 |
| 可执行 | 可重复调用入口和计算验证通过，依赖满足 | 可以回答登记范围内的实际问题 |

登录失效、权限变化、字段变化属于当前运行可用性；失败时停止依赖它的统计，不把上次结果充作现查。一个数据域失败，仍可完成与它无关且已验证的部分。

初期用现有参考中的能力表管理即可。不先建立额外机器注册中心；只有实际出现自动检查依赖/生成帮助的需要，再从唯一配置生成展示，避免手工维护多份状态。

## 指标与计算

每个可复用指标建立“指标卡”：ID/版本、业务含义、粒度、单位、期间及业务时间、公式、纳入/排除、输入依赖、缺失值规则、套装/单位处理、验证样例、执行入口和当前状态。

优先复用的指标家族：

- 默认在售 SKU 数、有效订单商品件数、销售日序列及可比期间贡献。
- 实际净可履约库存、有效未收到货及到货时间、加工预期入库。
- 需求与库存错配候选、供给时序缺口、覆盖天数及补货/补产情景。
- 有库存日期证据后的库存年龄、经确认成本后的占用金额。
- 有工序记录后的首次合格、返工、报废；有完整成本链路后的成本/毛利。

这些是建设顺序，不能视为都已实现。默认销售件数与库存消耗分开：赠品、换货、补发不参加既有销量指标，但可能消耗实物。正常销售、售后净销售、出库消耗也各有独立定义。

记录缺失与业务零值分开；单位未核实时不跨商品相加；费用项不算实物资产；共享组件不重复计供给。金额用明确的币种、精度和舍入规则。预测也是计算能力，留出历史截点、方法、参数和回测结果，模型只解释已计算结果。

指标修改不能静默覆盖旧口径。变更业务定义时新增/升级指标版本，标明是否仍与历史结果可比；实现修复则保留定义并补针对性回归。

## 模块分析卡

每个模块使用统一的维护结构，实际回答按问题选择内容：

1. 目标问题与预期动作：用户要决定什么，涉及哪些范围。
2. 必需/可选数据与可用状态：缺少哪项将影响哪种结论。
3. 引用的指标卡与参数：不在模块里另抄一套公式。
4. 分析步骤：从事实与异常到解释，需要什么证据区分原因。
5. 缺数据时的输出：可靠事实、候选、显式假设情景或具体缺项。
6. 交付字段与可追溯依据：量、单位、期间、来源、行动及约束。
7. 示例与验收：正常问题、误判边界和依赖缺失；分清构造数据与实际证据。

### 六类问题如何沉淀

| 模块 | 推荐流程 | 缺项时的处理 | 示例问题 |
| --- | --- | --- | --- |
| 产销与需求 | 核对历史覆盖/分类 → 可比销量和渠道贡献 → 大单/活动/缺货影响 → 与库存及供给匹配 → 预测或需求情景 | 无缺货历史时承认销量可能受库存限制；无成本时按需求/周转分组，不称高利润 | 哪些款卖得好却缺货？最近增长来自哪个渠道？ |
| 库存与半成品 | 类型/单位/货权 → 库存及入库证据 → 未结加工对账 → 批次实际状态 → 剩余工艺与需求 → 处理候选 | 单头未结先核对；没有批次就不算真实停滞时长/工序积压 | 哪些半成品值得继续做？哪些老加工单需要核对？ |
| 补货与补产 | 需求/实际供给 → 有效采购及加工到货时序 → 首次缺口 → 交期及工艺约束 → 数量/日期建议 | 无 ETA/交期只做标注假设的情景；工艺条件未核实不直接排到员工 | 未来一个生产周期要补什么？已有在途够不够？ |
| 工序、人效与计件 | 批次投入/产出对齐 → 首次合格/返工/报废 → 区分等待与加工 → 工艺难度/团队分组 → 核算和异常复核 | 无报工/质检则给采集缺项；不从最终入库推个人贡献或自动扣罚 | 哪道工序返工多？一批货计件应如何核对？ |
| 成本与经营复盘 | 金额口径 → 成本凭据与分摊 → 售后/费用影响 → 产品贡献与资金占用 → 账务核对及行动 | 只有售价或采购价时输出局部估算及缺项，不报完整净利润 | 哪些款值得优先生产？库存占用了多少自有资金？ |
| 新品辅助 | 现有偏好/复购证据 → 库存与渠道 → 打样/工艺可行性 → 小批假设 → 上市验证 | 没有外部市场/试制数据时只提出试验方向，不预测成功率 | 新品先做哪种器型、工艺和价格带？ |

动态逐工序排程是补产流程的后续能力，需要生产现场约束和真实批次状态；先做可核对的优先级建议。不能从订单表一步跳到全厂每日任务。

## 示例：如何检验 skill 的决策

以下数字均为构造示例，不是任何企业实际经营结果；尚未接入的能力只用于定义期望行为，不提供虚构的可执行命令。

### 已有直接查询

问题：“本月销量最好的商品，显示10个。”

调用已有 `scripts/query.sh sales-top --limit 10`，沿用已确认口径。本月期间按运行时间计算，仅在成功且请求范围完整时报告商品、SKU、件数、查询时间和口径。无需加载成本/工序参考，不能直接回答这些商品利润最高或应扩产最多。

### 库存口径陷阱

问题：“这个 SKU 能撑几天？”假设近期每天新增需求5件，ERP在售可用数100件，其中80件是虚拟库存；经库存字段核对，净实物可履约量只有20件，且已扣占用。

若这些输入均已接入验证，简化恒定需求且无到货情景下为4天，不是20天，也不重复扣订单占用。没有库存拆分时，明确只能确认在售字段，不能给可靠实物覆盖天数。必须说明这里是需求情景，未包含波动、未来供给或服务水平保证。

### 老加工单陷阱

问题：“这张4月加工单是不是积压了半年？”单头未入库，但备注写作废。

先核对有效状态、红冲、收货和是否仍有对应实物；若只有单头证据，输出“旧未结单，需核对”，不输出“半成品实际停滞半年”。有实物后还需当前工序及暂停起止才能计算停滞。

### 补货量与到货时序

问题：“未来30天该补多少？”假设新增需求10件/天、净可履约50件、第20天到货100件、安全量和未计承诺需求均为0。

总量缺口为150件，但无更早供给时约第6天已出现不足。不能仅给150件并称缺货已解决；需给到货前缺口及更早供给/调整承诺的候选动作。交期未知时不编造最迟下单日。生产场景需另核对完成剩余工序所需时间。

### 部分数据与利润问题

问题：“这个月哪些款最赚钱？”只有订单数量/金额，没有成本和费用。

核对金额口径后可给销量/成交金额贡献，指出成本链缺项，不能把金额榜改名利润榜。若订单读取失败或期间缺页，不发布全月成功榜；与缺失成本无关的已验证销量查询仍可执行。

## 建设批次及验收

| 批次 | 具体交付 | 验收条件 |
| --- | --- | --- |
| 0：本轮设计 | 分层、契约、模块规范、例子及能力边界 | 文档引用可达，现有命令与口径保持一致；未实现项明确 |
| 1：销售与库存错配 | 商品分类/单位/货权核对；限定期间全量销售日明细；实际库存；错配候选表 | 全期分页及关联对账；缺日期不填零；排除费用/来料误计；套装/组件边界通过；小范围真实复核 |
| 2：采购与加工未结核对（已落地） | 当前非归档SKU、收货、账面剩余、日期来源及加工原料单号关联 | 分批、作废提示、未关/旧单、超收、重复供给回归通过；已核实进仓正负冲回按净量核对，未知退货类型/负净收停止；缺日期与采购头总量占位可见，加工头及收货对账；逐行BOM待接 |
| 3：补货与补产情景（已落地） | 前两批事实＋完整日直接订单基线/误差＋显式周期与可用批次形成情景量和日期 | 总量、到货前缺口、负库存/占用、包装MOQ、供给去重及缺项校验；订单数量向前验证非完整策略回测；BOM/实际消耗/工序政策仍待验收 |
| 4：现场与财务扩展 | 按试点复用或补入工序/质检/成本记录，逐模块开放 | 批次投入产出、人员/工艺、成本凭据及分摊可以核对；再验证排程或利润，不能用方案时间表代替数据验收 |

每批交付都包含读取/计算能力、模块流程、至少一个有来源的案例和关键失败边界。先让一条端到端分析链可用，再扩展数据域；不要先把所有 API 盘完才交付。
